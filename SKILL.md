# Атлас опыта · Experience Atlas

## Когда активировать

- Пользователь готовится к поиску работы после перерыва или долгого стажа в одной компании.
- Есть **файл грейдов** (или аналог матрицы компетенций) и **целевой грейд**.
- Нет собранного портфолио или «в голове много, но не помню кейсы».
- Нужна **база кейсов**, а не сразу красивый PDF.

## Вход пользователя (обязательно)

1. Путь к **рабочей папке сессии** (копия `template/`).
2. **`grade-matrix.md`** — описание уровней и параметров (может быть вне репо).
3. **Целевой грейд** одной строкой (например: Middle Product, Senior UX Writer).
4. Опционально: резюме, 1–3 JD, `_career_context.md` (1 абзац о себе).

## Жёсткие правила

1. **Один вопрос за сообщение** в фазе recall (если пользователь не просит иначе).
2. **Не выдумывать** метрики, роли, масштаб. Неизвестное → `template/_deferred_facts.md`.
3. **Не читать лишние файлы** — только сессия пользователя + приложенная матрица грейдов.
4. **Readonly:** исходные материалы пользователя не перезаписывать; новые кейсы только в `cases/` сессии.
5. Помогать **доставать недооценённый опыт**: «мелочь», «не моя зона», «давно было».
6. Negative / neutral results — **валидный исход**, не приукрашивать.
7. При смене целевой роли — добавлять `role_framing`, не менять факты в STAR.

## Фазы работы

### Phase 0 — Setup

Убедиться, что в сессии есть:

- `_CONTINUITY.md` — решения без истории чата (обновлять).
- `_coverage_map.md` — параметр грейда → статус → case ids.
- `_deferred_facts.md` — что уточнить у пользователя.
- `_business_outcomes_index.md` — индекс для найма (заполнять постепенно).
- `cases/` — JSON-кейсы.
- `grade-matrix.md` — копия или ссылка на путь (в `_CONTINUITY`).

Кратко показать пользователю план: сколько параметров, с чего начнёте.

### Phase 1 — Coverage map

Из `grade-matrix.md` для **целевого грейда** извлечь блоки компетенций.

Для каждого параметра в `_coverage_map.md`:

- `status`: `есть` | `частично` | `нет` | `N/A`
- `priority`: `must` | `should` | `nice` (must — то, без чего не пройдёт найм на грейд)
- `case_ids`: [] 

Показать пользователю сводку: что уже закрыто, где пробелы.

### Phase 2 — Recall loop (ядро)

Для каждого параметра без кейса (приоритет must → should → nice):

1. **Один открывающий вопрос** — широкий, без наводки на «правильный» ответ.
2. Уточнения: сигнал, гипотеза, действие, исход, **метрика**, **ownership**, стейкхолдеры.
3. Если пользователь «ничего не было» — якорные вопросы (см. ниже).
4. По завершении блока — записать `cases/{slug}.json` по `schema/case.schema.json`.
5. Обновить `_coverage_map.md`, при необходимости `_business_outcomes_index.md`.
6. Обновить `_CONTINUITY.md`.

### Phase 3 — Reframe (опционально)

Если прошлая роль ≠ целевая (UXW → PM, analyst → PM):

- Добавить объект `role_framing` в кейс (см. схему).
- Переписать **линзу** (situation/task/outcome), не факты.
- Явный `ownership_note`: что было твоим, что — совместным.

### Phase 4 — Export

- Дописать `_business_outcomes_index.md` (язык outcomes, не «согласовал экран»).
- Список пробелов в `_deferred_facts.md`.
- По запросу — передать `prompts/site-build.md` с путём к сессии.

## Якорные вопросы (если «не помню»)

- Был ли **сигнал** из поддержки, аналитики, продакта, метрики?
- **Спор** со стейкхолдером — чем закончился?
- **Гипотеза не выстрелила** — что сделали дальше?
- Что **инициировал** без формального мандата?
- Где **сэкономили** команде rework, время, деньги?
- Что казалось **мелким**, но без тебя сломалось бы?
- **Кросс-команда** / multi-owner — как синхронизировали?

## Формат кейса

См. `schema/case.schema.json`. Минимум: STAR + `target_grade_parameters` + `role_framing.business_problem_headline`.

## Антипаттерны

- ❌ Генерировать 10 кейсов за один ответ.
- ❌ Портфолио = список задач без business outcome.
- ❌ Выдуманные проценты конверсии.
- ❌ Игнорировать partial ownership — это норма для перехода в PM.

## Связанные файлы в репо

- `prompts/session-start.md` — промпт для пользователя.
- `prompts/site-build.md` — сборка сайта из сессии.
- `examples/case.example.json` — образец.
